# Gemtek W1700K on this branch

Snapshot of the current state of W1700K support. Not a changelog — if something
below stops being true, edit or delete it.

## Status

Both units run this branch **installed on flash** and are fully working: all four
wired ports, tri-band wireless, and 5 Gbps on the 10G ports. `sysupgrade` is
exercised and safe.

| unit | serial | role |
|---|---|---|
| `5867a0` | | deployed as `W1700K-C3` — behaviour under real clients |
| `5cd3a0` | `W1700K2614011441` | bench — replaces `WAX206-S1` |

Changes are proven on `5cd3a0` before `5867a0` is sysupgraded; syncing the deployed
unit early restarts its soak and costs the signal it exists to provide.

Stock on `5867a0` is no longer factory: the first 1 MiB of `tclinux` is overwritten
by the chainloader, the device flashed itself an AXON update, and its config overlay
carries our SSH edits. There is **no stock backup** for it — abandoned deliberately.
`5cd3a0` does have one: `vendor` and `reserved_bmt`, md5-verified against the device,
in `w1700k-capture/unit-5cd3a0/`. See *Backing up stock*.

The label reads 2.1 and the stock firmware reports `Unit is W1700K HW v2`, so this
is a newer major revision than the **v1** the OpenWrt wiki documents. Flash
geometry and the stock partition table are identical to v1's, which is what the
install depends on — but **the 10G PHY is different silicon**, which is not
cosmetic and is covered under *10G ports*. Expect any further unit to be v2 and
check the PHY ID rather than assuming.

Note `DEVICE_COMPAT_VERSION := 2.0` in the image recipe is OpenWrt's flash-layout
compat version. It has nothing to do with the vendor's HW 2.1 label.

### Verified on unit 1 (HW v2, from the stock boot log)

| | |
|---|---|
| NAND | Winbond **W25N04K**, `Flash Size=0x20000000` |
| geometry | **512 MiB SLC, 128 KiB erase, 2048 B page, 128 B OOB** — matches `BLOCKSIZE`/`PAGESIZE` |
| stock partitions | 10, identical to the wiki's v1 table |
| `system` end | **`0x1be00000`** — exactly where our `reserved_bmt` starts, so compat 2.0 is right |
| bootloader | U-Boot 2014.04-rc1 (Dec 03 2025), **AXON 2.3** |
| DRAM | PCDDR4 @ 2666, DRAMC V0.9, ~2 GiB (`1855584K/2095872K`) |
| SoC identity | `model: econet` (Airoha's legacy EcoNet name) |

AXON **2.3** is newer than any version the wiki discusses (it calls 1.6
troublesome and 2.0 better), so TFTP reliability is unknown rather than known-bad.

**10G PHYs confirmed at the addresses our DTS expects.** Stock loads
`rtk-rtl8261ce-phy.ko` and probes:

```
Realtek RTL8261CE mdio-bus--1:05  rtl8261ce addr:5
Realtek RTL8261CE mdio-bus--1:08  rtl8261ce addr:8
[rtkphy_config_init] phy_id: 0x1CC890 PHYAD:8
```

Addresses 5 and 8 match `phy5`/`phy8` exactly, and the vendor's probe symbol is
`rtl826xb_probe` — the same Realtek SDK our `kmod-phy-rtl8261n` is built from.

`0x001CC890` is a red herring: it is the **C22** identity (mainline calls it
`RTL_8261C` and gates it behind `if (phydev->is_c45) return false`). Our DTS
declares `ethernet-phy-ieee802.3-c45`, so phylib reads the **C45** ID from MMD1
PMA/PMD instead, which for this family is `0x001CCAF3` — the `RTL8261N` entry our
driver matches. Mainline likewise matches every 10G part in the family
(`8251L`, `8261BE`, `8261N`) through `rtlgen_is_c45_match(…, RTL_8261N, true)` and
separates them by vendor `PKG_MODEL`/`VERSION_ID` registers. Master's vendor
driver carries the same three IDs as ours, and that is the driver upstream shipped
for this device.

Confirm after flashing: `dmesg` should show `Realtek RTL8261N` attaching at mdio
addr 5 and 8. If it does not, add `0x001CC890` as a fourth `phy_driver` entry
classified as `RTK_PHYLIB_RTL8261N` — the driver already ships the matching
C-revision blob, `construct/conf_rtl8261n_c.c` (`rtl8261n_c_top_conf[]`).

Also unconfirmed: the **NCT7802** fan controller at i2c `0x2e`. Stock never
mentions it (it drives i2c through its own `ecnt_i2c` stack and only logs the
SoC's `7581 Thermal PHY`), and `fan_id=asink_w1700k_v2` hints the assembly is
revision-specific. Worth checking early, since the fan is the only working thermal
mechanism — cpufreq throttling is inert, see *Thermal*.

Stock does not offer a console login — it settles into an Axon provisioning loop
(rewriting `mapd_user.cfg` / `dpp_cfg.txt`, presumably unable to reach the ISP).
Root access needs the failsafe window: `Press the [f] key and hit [enter] to enter
failsafe mode`, roughly 12–13 s into boot.

## Hardware

| | |
|---|---|
| SoC | Airoha AN7581 |
| CPU | 4x Cortex-A53, 500–1200 MHz (50 MHz steps) |
| RAM | ~2 GiB (PCDDR4) — per the v1 wiki bootlog, unconfirmed on 2.1 |
| Flash | 512 MiB SPI-NAND, 128 KiB erase, 2048 B page |
| Wi-Fi | MT7996AV, tri-band (2.4 / 5 / 6 GHz), PCIe |
| 10G PHYs | 2x Realtek RTL8261CE (NBASE-T) at MDIO 5 and 8, resets on GPIO 46 / 31 — C22 ID `0x1CC890` on both units; see *10G ports* |
| Switch | MT7530, provides `lan3` / `lan4` at 1G |
| Fan | Nuvoton NCT7802 hwmon at i2c `0x2e` |
| Other | Airoha GPS on `/dev/ttyS2` @ 460800; BT and Zigbee present |

Ports: `wan` and `lan2` are the 10G USXGMII ports (`gdm2` / `gdm4`); `lan3` and
`lan4` hang off the switch. The RTL8261N is NBASE-T, so a 2.5G backhaul
negotiates natively — nothing extra is needed for it.

Power: **12 V 4 A** (48 W) on both the device label and the supplied brick. The
barrel is a **6 mm** type, not the common small 5.5 mm — worth knowing before
buying a replacement.

### Inside (observed on 2.1)

- Massive custom aluminium heatsink, held by screws from the far side of the board
- **60 x 60 mm fan** — this is the real thermal mechanism, see *Thermal*
- **11 populated antenna connectors**: 2 + 3 on the side opposite the Ethernet
  ports, 4 + 2 along one edge. Consistent with a high stream count on 5/6 GHz plus
  auxiliary radios; `iw phy` after flashing gives the actual chain config
- Board held by 4 Phillips screws
- **J5 — 5-pin, populated: the serial console.** Matches the documented
  `TX - GND - VCC - N/A - RX` (five positions, one unused)
- **J24 / J25 — 4-pin each, unpopulated**, along the opposite edge. Unidentified;
  plausibly the JTAG the wiki has an empty section for

### Serial

**115200**, on J5, pin order `TX - GND - VCC - N/A - RX` with the Ethernet ports
facing you. **Do not connect VCC.** Wire adapter RX to J5 TX, adapter TX to J5 RX,
GND to GND; leave VCC and the unused pin alone.

Confirm orientation with a meter rather than trusting the printed order — the wiki
was already wrong about the case screw. GND reads continuity to the heatsink or
shield; the SoC TX idles high. Also check the VCC pin reads **3.3 V and not
1.8 V** before connecting a 3.3 V adapter, since a 3.3 V TX into a 1.8 V RX can
damage the SoC. The wiki's table indicates 3.3 V, but measure on 2.1.

The pins are also reachable through the case slits with a spider board, so the
case does not strictly have to come off.

Opening the case on our 2.1 units: a single screw sits in a deep recess **below**
the QR code, not behind it. It takes an **Allen key** — the drive is an internal
hex socket, not an external hex head. The wiki calls it T10 Torx; that is
untested here, because a Torx driver could not reach the depth, and a hex key will
sometimes turn a Torx socket anyway. Either way an Allen key works.

Depth is the real constraint, not the bit type: use a long-arm Allen key, or drop
a hex bit into the recess and fit the driver over it (the wiki's trick — it wants
a bit around 1-1/8 in / 29 mm or longer). Then work a thin blade into the seam at
the LAN ports to release the clips.

## Flash layout

Ours (compat 2.0), tiling the chip exactly with no gaps:

| mtd | label | offset | size | |
|---|---|---|---|---|
| 0 | vendor | `0x00000000` | 6 MiB | read-only |
| 1 | chainloader | `0x00600000` | 1 MiB | |
| 2 | ubi | `0x00700000` | 439 MiB | |
| 3 | reserved_bmt | `0x1be00000` | 66 MiB | read-only |

Stock, for comparison: bootloader 2 MiB, uenv 2 MiB, dsd 2 MiB, tclinux 64 MiB,
tclinux_slave 64 MiB, system 312 MiB, reserved_bmt 66 MiB.

Our `vendor` is exactly stock's bootloader + uenv + dsd, and both it and
`reserved_bmt` are read-only. So installing OpenWrt **preserves** the stock
bootloader, its environment, the DSD (MACs, serial, fan_id), the Wi-Fi EEPROM and
the bad-block table. It overwrites `0x600000`–`0x1be00000`, i.e. stock tclinux +
tclinux_slave + most of system.

`reserved_bmt` at 66 MiB is what makes this compat 2.0; the 1.0 layout had 2 MiB
there and 503 MiB of ubi. The u-boot side must agree, and does — this branch
carries `4729793b91`.

## Build

`build_me.pl airoha an7581` then `make`. Two passes, because the installer image
embeds the images the first pass produces.

```sh
./build_me.pl airoha an7581
make -j"$(nproc)"

# pass 2 — installer image. Must not go through build_me.pl, which empties
# bin/targets. Dropping the base device matters: leaving it selected rebuilds its
# images after the payload is copied, so what ships would differ from what is
# embedded.
sed -i '/^CONFIG_TARGET_DEVICE_airoha_an7581_DEVICE_gemtek_w1700k-ubi=y$/d' .config
echo 'CONFIG_TARGET_DEVICE_airoha_an7581_DEVICE_gemtek_w1700k-ubi-installer=y' >> .config
make defconfig && make -j"$(nproc)"
```

Artifacts in `bin/targets/airoha/an7581/`:

| file | size | |
|---|---|---|
| `…-chainload-uboot.itb` | 276K | the only transfer through the stock bootloader |
| `…-initramfs-recovery.itb` | 22M | full OpenWrt in RAM, no installer |
| `…-squashfs-sysupgrade.itb` | 24M | |
| `…-installer-initramfs-recovery.itb` | 66M | auto-installs on boot |

The installer device sets `KERNEL_LOADADDR := 0x92000000`. It carries both
payload images, so its kernel decompresses to ~74 MiB, while the default
`0x80200000` has only 62 MiB before the first NPU carveout at `0x84000000` —
`bootm` then fails with `Unable to allocate memory 0x80200000 for loading OS`.
Upstream's installer fits because its package set is smaller; ours does not.
`KERNEL_LOADADDR` is in `DEVICE_VARS` and only feeds `mkimage -a/-e`, so this is
FIT metadata, not a kernel relink. Land above every reserved-memory region — the
last, `npu-ba`, ends at `0x90e067ff`.

An already-transferred image can be relocated in place without re-sending it:
`fdt addr <addr>` then `fdt set /images/kernel-1 load <0x92000000>` and the same
for `entry`. Both are 4-byte cells, so the splice is in place and the hashes
still verify — check with `iminfo`.

**Acceptance test:** the two images embedded at `/installer/` inside the installer
must be `sha256`-identical to the flashable ones. Checking the manifest for
`wpad-mbedtls …-r2` is not sufficient — a stale payload can ship unpatched
firmware while `bin/` looks correct.

## Install

Stock U-Boot only `bootm`s signed images, so the chainloader must be flashed before
any of our images can boot. That write erases `0x600000`–`0x700000`, the **first
1 MiB of stock `tclinux`**.

Rooting stock is **not** required. The whole flow runs from the stock U-Boot prompt
plus the console, and the backup is better taken afterwards (see *Backing up stock*).

1. **Validate the geometry.** This is the go/no-go, and it is readable straight off
   the stock boot log — no root needed. Confirm the NAND (`Winbond
   _SPI_NAND_DEVICE_ID_W25N04K`, 512 MiB, 128 KiB erase, 2048 page, 128 OOB) and the
   partition offsets, in particular that `system` ends at `0x1be00000`, exactly where
   our `reserved_bmt` starts. The log also gives `Unit is W1700K HW v2`, the PHY ID
   and the AXON version. **Stop if the geometry differs from the table above** — the
   installer would `ubiformat` against a wrong map.
2. **Chainloader.** Interrupt autoboot, YMODEM it in, verify with `crc32`/`iminfo`,
   then erase+write and `saveenv`. See *Talking to stock U-Boot*; keep
   `bootcmd_orig` so there is a way back to stock.
3. **Installer.** From the chainloader, TFTP and boot the installer image — its
   U-Boot has a working TFTP, so this is fast. It validates the DSD (echoing
   `wan_mac`, `lan_mac`, `fan_id`, `serial_number`), rebuilds the factory volume,
   prompts `Existing UBI layout detected. Proceed and overwrite? (yes/no)`,
   `ubiformat`s and reboots.

Block internet to the device for the duration. Given a NATed uplink it will flash
itself an AXON update, which rewrote `bootloader` and `tclinux` on both units here.

### Rooting stock

Verified on HW v2. The wiki's route through the config files turns out to be
necessary, for reasons the wiki does not give.

**Failsafe gives root but no usable network.** Send `f` + enter at `Press the [f]
key and hit [enter] to enter failsafe mode` (~12–13 s in). You get a root shell,
dropbear already listening on 192.168.1.1/24, and `nanddump`, `nandwrite`, `dd`,
`nc`, `ubinfo`, `gzip`, `openssl`, `chpasswd`, `swconfig`, `ethtool`. But failsafe
never runs the vendor SDK's switch init, so the forwarding matrix is unprogrammed:

- broadcast passes **both** directions (the device sees our ARP requests; we see
  its ARP requests)
- unicast is dropped in **both** directions — so ARP never resolves and nothing
  works above L2

`/proc/tc3162/gsw_link_st` still shows the link as real (`Port1 : 1000M/Full`,
CPU `Port6 : 1000M/Full`), and `swconfig list` returns nothing — there is no
registered switch to configure. Promiscuous mode and moving the address onto
`eth0.1` both change nothing. The device's failsafe MAC is a placeholder
`00:aa:bb:01:23:40`, not the DSD `lan_mac`.

**Serial is not a workaround.** Measured throughput of the vendor console is
~220 B/s, far below the 115200 line rate, so even the irreplaceable 6 MiB would
take hours. (`base64` is absent from the device busybox; `openssl base64` works.
Watch out for the console echoing commands back wrapped at 64 columns — a marker
like `B64START` will match inside the echoed command, so emit it as
`echo "B64""START"`.)

So: `mount_root`, edit the two config files, reboot into normal mode where the
SDK initialises the switch properly, and use SSH.

`mount_root` mounts a UBIFS overlay (`ubi0_0`) read-write, i.e. it **writes to
flash** — inside `system`, the partition our install wipes anyway. It does not
touch `bootloader`, `uenv` or `dsd`.

Both files must be edited, because the Axon manager rewrites `/etc/config/*` from
its own database at boot and would otherwise clobber the dropbear change.

`/etc/config/dropbear` ships as `enable '0'`, `RootLogin '0'`,
`RootPasswordAuth '0'`, `chroot '/mnt/chroot'`. Replace it wholesale:

```sh
printf "config dropbear\n\toption PasswordAuth 'on'\n\toption RootPasswordAuth 'on'\n\toption Port '22'\n" > /etc/config/dropbear
echo 'root:<password>' | chpasswd
```

`/etc/config/axon_platform_manager` is a 216 KB JSON blob. Two edits:

```sh
sed -i 's/"sshServerEnable": "0"/"sshServerEnable": "1"/g;
        s/"remoteAccessEnable": "0"/"remoteAccessEnable": "1"/g;
        s/"localAccessEnable": "0"/"localAccessEnable": "1"/g' /etc/config/axon_platform_manager
```

and five firewall rules held as a URL-encoded string with `%25252c` separators —
three `SSH`, one `Local SSH`, one `Remote SSH`, all `Drop`, the latter two also
`Disabled`:

```sh
sed -i 's/%25252cSSH%25252cDrop/%25252cSSH%25252cAccept/g;
        s/%25252cLocal SSH%25252cDrop/%25252cLocal SSH%25252cAccept/g;
        s/%25252cRemote SSH%25252cDrop/%25252cRemote SSH%25252cAccept/g;
        s/Disabled%25252c1%25252cLocal SSH/Enabled%25252c1%25252cLocal SSH/g;
        s/Disabled%25252c1%25252cRemote SSH/Enabled%25252c1%25252cRemote SSH/g' /etc/config/axon_platform_manager
```

Then reboot into normal mode.

### Getting on the network — the device is a DHCP *client*

Only relevant to the optional *Rooting stock* path, which needs a lease so stock's
dropbear is reachable. The install itself does not: stock U-Boot uses static IPs, and
there the better host setup is an NM-unmanaged interface with a static address (see
*Talking to stock U-Boot*).

A factory unit is unprovisioned, and it never serves DHCP on **any** port. Plugged
into the yellow 1G LAN port it emits, continuously:

```
BOOTP/DHCP, Request from 84:70:03:58:67:a0     <- wan_mac
PPPoE PADI [Service-Name]
IEEE1905.1 (0x893a)   STP 802.1d
```

i.e. it is hunting for an uplink on every port and acting as a Multi-AP/EasyMesh
agent (`mapd_user.cfg`, `allowed_role = 1` written on loop). So do not wait for a
lease — **give it one**.

Easiest: set the wired interface to NetworkManager's **Shared** method. The host
becomes 10.42.0.1/24 and the device takes a lease (10.42.0.218 on unit `5867a0`);
find it with `ip neigh show dev <iface>`, matched by `wan_mac`.

Caveat, and it is not hypothetical: Shared mode also NATs, so the device gets
internet. **Both units used that window to flash themselves a bootloader update** —
AXON 2.3 (built Dec 2025) became AXON 2.5 (built Apr 2026) between boots, which
also means `bootloader` and almost certainly `tclinux` were rewritten, so a
"factory" backup taken afterwards is not one. Block forwarding before letting the
device sit on a NATed link:

```sh
sudo iptables -I FORWARD -i <iface> -j DROP
```

SSH is then plain dropbear with the password set above. This host has no
`sshpass`/`expect`/`paramiko`, so drive it non-interactively with OpenSSH's
askpass override:

```sh
printf '#!/bin/sh\necho <password>\n' > .askpass && chmod +x .askpass
export SSH_ASKPASS=$PWD/.askpass SSH_ASKPASS_REQUIRE=force
ssh -o StrictHostKeyChecking=no -o PubkeyAuthentication=no root@10.42.0.218 id
```

### Backing up stock

**Do this after installing, not before.** The install never writes the first 6 MiB —
our read-only `vendor` partition is exactly stock's `bootloader` + `uenv` + `dsd` — so
everything irreplaceable survives it. Backing up from stock costs the whole
*Rooting stock* detour (failsafe, config edits, reboot) to capture bytes the install
preserves anyway, whereas post-install it is a two-command network copy. What a
pre-install backup uniquely saves is `tclinux`/`tclinux_slave` (the vendor OS,
downloadable from the vendor URL the wiki cites) and `system` (config and logs,
~all erased) — which is why it is not worth the detour.

Done for unit `5cd3a0`, md5-verified against the device, in
`w1700k-capture/unit-5cd3a0/` alongside an `INFO.txt` recording the DSD values,
serial and installed image hashes:

```sh
ssh root@<device> 'md5sum /dev/mtd0'          # compare against the copy
ssh root@<device> 'cat /dev/mtd0' > mtd0-vendor.bin        #  6 MiB  vendor
ssh root@<device> 'cat /dev/mtd3' > mtd3-reserved_bmt.bin  # 66 MiB  reserved_bmt
```

`reserved_bmt` cannot be captured from stock at all — it has no mtd device there.
Our layout maps it as `mtd3` read-only, so it is unchanged after flashing.

If a pre-install dump is ever wanted anyway, take the six *top-level* partitions —
`bootloader`, `uenv`, `dsd`, `tclinux`, `tclinux_slave`, `system` (446 MiB) — and skip
`kernel`, `rootfs`, `kernel_slave`, `rootfs_slave`, which are sub-partitions of
`tclinux`/`tclinux_slave` and duplicate bytes already captured. Per partition: one
NAND read into the device's tmpfs, md5 there, gzip-stream out, then compare the
decompressed md5 on the host — see `backup.sh` in the capture directory. At ~3.7 MB/s
the set is a couple of minutes. Note stock U-Boot cannot help: it has `flash read` but
no egress path (no `tftpput`, no USB, no mass storage), and `md` over a ~220 B/s
console makes even the 6 MiB an overnight job.

### Talking to stock U-Boot

Verified on AXON 2.5. Every rule below cost at least one power-cycle to learn.

**Interrupt it automatically.** Watch the console capture for `Hit any key to stop
autoboot` and write newlines the moment it appears; the window is ~4 s. Doing it
by hand is a coin flip.

**On AXON 2.3 the prompt does not hold.** Roughly 4 s after input stops the board
resets — the last `ECNT>` is followed by `Secure key exist` and a full
`AN7581DRAMC V0.9` re-init — so reaching the prompt is not enough there and a
keepalive is required (a bare newline every 2 s; a no-op at the prompt). **2.5 holds
the prompt indefinitely.** A factory unit ships 2.3 and updates itself to 2.5 given
internet, and 2.5 is what everything here is verified against.

**Do not try to TFTP from stock U-Boot — use YMODEM.** Its `ecnt_eth` TFTP client
stalls after exactly two 512-byte blocks (`Loading: *##T #T #T …`, then `Retry count
exceeded`) and no amount of retrying or power-cycling changes that. It is not the
environment: it reproduces identically with a 1 Gbps link at 0.1 ms RTT, the
interface in firewalld's `trusted` zone, a verified-working server, and
`tftptimeout`/`tftpblocksize`/`tftptimeoutcountmax` all raised. Meanwhile the host
sends ~15 000 packets per attempt and drops none, so the data is on the wire and the
device is not taking it. The wiki's "flaky TFTP, try up to six power-cycles" is this
defect; retrying does not fix it.

`loady` works and only the 276 KB chainloader has to come through here, so the
console is a perfectly adequate transport — ~6.1 KB/s, about 46 s:

```sh
# in U-Boot
loady 0x89000000
# on the host, with NOTHING else holding the tty (a console-capture `cat` steals
# the ACKs sz needs), then restart the capture afterwards
sb --ymodem chain.itb < /dev/ttyUSB1 > /dev/ttyUSB1
```

U-Boot prints `## Total Size = 0x00044e98 = 282264 Bytes` — YMODEM carries the true
length in its header, so the block padding does not inflate it. Verify before
writing: `crc32 0x89000000 0x44e98` against the host's, and `iminfo 0x89000000`.

Once the chainloader is in, **its** U-Boot has a working TFTP (562 KiB/s, the 69.6 MB
installer in ~2 min), so this is the only transfer that needs YMODEM.

**Only the yellow 1G LAN port works.** `ping` from U-Boot answers there and fails
on both 10G ports — the bootloader never brings up their SerDes/PCS, matching the
`invalid(10G)` entries for `Port0`/`Port5` in `gsw_link_st`. The wiki says to use
the yellow port and it is right.

**Stock U-Boot's `ping` gives false negatives.** It reports `host is not alive` on a
link that provably works, because `ecnt_eth` polls its RX ring too seldom to catch a
single reply. Ping the *device* from the host instead: that still proves device RX,
device TX and host RX, and it succeeds reliably (0.1 ms on a healthy 1 Gbps link).
A failed `tftpboot` is recoverable — `Ctrl-C` twice returns to `ECNT>` cleanly.

**The console drops input characters** written at full speed with no flow control:
`printenv ethact` arrived as `printenvact`. Send character-by-character with a few
ms between; `docs/tools/sertx` does this. Do not type `flash` commands at speed.

**Use `docs/tools/tiny-tftpd.py`, not atftpd.** atftpd failed even to a local
`curl` here, and its RFC extensions break this U-Boot outright: option negotiation
produces `TFTP error: First block is not block 1`. The bundled server never sends
an OACK, serves plain 512-byte RFC1350, runs as the invoking user (atftpd drops to
`nobody`, which cannot read a home directory — hence `File not found`), and
threads each transfer so a stalled one cannot leak stale blocks into the next
request.

```sh
sudo docs/tools/tiny-tftpd.py /tmp/w1700k-tftp 10.42.0.1
```

Stage files somewhere world-readable such as `/tmp`, not under `$HOME`.

**firewalld: put the interface in the `trusted` zone.** Adding the `tftp` service
to `nm-shared` is *not* enough — the initial request gets through but most of the
data stream is dropped. A local `curl` test passes regardless, because loopback
bypasses the interface zone, so it never proves the device can reach the server.

```sh
sudo firewall-cmd --zone=trusted --change-interface=<iface>
```

**The zone is silently lost if the interface leaves NetworkManager.** After
`nmcli device set <iface> managed no` the interface reads `no zone` and falls back to
the default (`public`), which blocks ICMP and UDP/69 — indistinguishable from device
failure. Re-apply with `firewall-cmd --zone=trusted --add-interface=<iface>`; both
`firewall-cmd` calls go through polkit and need no `sudo`.

**Prefer a static address on an NM-unmanaged interface over NM Shared.** Shared drops
its address the moment the link flaps — and a device reset flaps it — leaving the
server bound to an address that no longer exists, which it does not recover from
without a restart. Shared also NATs, which is how unit `5867a0` reached the internet
and flashed itself an AXON update. U-Boot uses static IPs, so neither DHCP nor NAT is
needed:

```sh
nmcli device set <iface> managed no
sudo ip addr add 10.42.0.1/24 dev <iface>
sudo ip link set <iface> up
sudo firewall-cmd --zone=trusted --add-interface=<iface>
```

Revert with `nmcli device set <iface> managed yes` — the installed OpenWrt wants a
DHCP lease, and an unmanaged interface will not serve one.

A `*##T #T #T` / `Retry count exceeded` signature therefore has two unrelated causes:
a host-side block (fixable, above) or stock U-Boot's broken TFTP client (not fixable
— use YMODEM). Distinguish them by whether the host's `tx_packets` climbs while
`tx_dropped` stays flat; if the host is sending and the device is not receiving, it is
the client.

A healthy transfer — this is the **chainloader's** U-Boot, the only one whose TFTP
works:

```
Loading: *########################################################
         562.5 KiB/s
done
Bytes transferred = 282264 (44e98 hex)
```

Then, to install the chainloader — the first genuinely destructive step, since
`0x600000` is the head of stock `tclinux`:

```
setenv bootcmd_orig "$bootcmd"
setenv bootcmd 'flash read 0x600000 0x100000 $loadaddr; bootm'
saveenv
flash erase 0x600000 0x100000
flash write 0x600000 0x100000 0x89000000
reset
```

`bootcmd_orig` preserves `flash imgread 2048;bootm`, which is the way back to
stock. The new `bootcmd` uses raw `flash read` rather than `imgread`, and that is
what bypasses the signature check — `bootm` itself does not verify, which is why a
RAM-loaded unsigned image boots fine. Keep `$loadaddr` literal.

### Booting this branch from RAM, before installing

Once the chainloader is in, `tftpboot` + `bootm` the plain recovery image. Nothing
is written, and it reaches a shell (`root@W1700K:~#`, so `board_name` resolves and
the feed's hostname table works). Confirmed there:

| | |
|---|---|
| DTS | `Hardware name: Gemtek W1700K (OpenWrt U-Boot layout) (DT)` |
| `/proc/mtd` | all four partitions, tiling 512 MiB, incl. `reserved_bmt` as `mtd3` |
| NAND | Winbond, 512 MiB, 128 KiB block, 2048 page, 128 OOB — from our own bootloader |
| NPU | probes, fw 0.1111 |
| GPS UART | `ttyS2` @ 460800 |
| DSD via our map | `dd if=/dev/mtd0 bs=1 skip=4194304` returns all four fields |

**The A53 has no ARMv8 Crypto Extensions.** `/proc/cpuinfo` reports only
`fp asimd evtstrm crc32 cpuid` — no `aes`/`sha1`/`sha2`/`pmull`. So the decision
not to copy mediatek's `CRYPTO_*_ARM64_CE` block into `kernel-airoha.seed` was
correct; those would have been dead code.

**Expect a wall of deferred probes on this boot, and do not panic.** They all have
one cause — there is no `factory` UBI volume yet, so the nvmem provider the DTS
points at does not exist:

```
Failed to find NVMEM device
platform 1fb50000.ethernet: deferred probe pending: (reason unknown)
platform 1fb58000.switch:   deferred probe pending
pci 0000:01:00.0: deferred probe pending: supplier 1fb50000.ethernet not ready
mt7996e: eeprom load fail, use default bin
WARNING: ... at __device_links_no_driver
```

Consequences worth knowing: **there is no networking and no USB in this state**
(only `lo`), so a backup cannot be taken from here, and the PHY/NCT7802 questions
cannot be answered either — `rtl8261n` loads as a module but nothing attaches
while the ethernet driver is deferring. UBI *does* attach and reports 3 user
volumes, but those are stock's (`rootfs_data`/`config`/`log`), found because our
`ubi` partition starts at 7 MiB and overlaps where stock's UBI lives.

All of it should clear once the installer creates the volumes.

### Installer behaviour

- **No prompt on a virgin device.** It looks for an existing `ubi0`; a factory
  unit has none, so booting the installer image *is* the install.
- **Fails safe on the wrong device.** Requires a DSD serial starting `W1700K`,
  `W1701K` or `XR1710G`, and dies before touching flash otherwise.
- It prints the decoded `wan_mac`, `lan_mac`, `fan_id` and `serial_number` before
  formatting. Read them. If they look wrong, power off — nothing is erased yet.
- It backs nothing up.

### Non-destructive alternative for inspection

The plain `-initramfs-recovery.itb` has no installer payload and no preinit hook.
`70_initramfs_test` breaks out of preinit before `80_mount_root`, so it never
mounts or writes flash. Useful for validating our DTB against the hardware:
`cat /proc/mtd`, `ip -br link`, `cat /sys/class/hwmon/*/name`,
`dmesg | grep -iE 'rtl8261|mdio|mt7530|mt7996'`, `cat /proc/cpuinfo`.

It reaches the network at 192.168.1.1 on `lan2`/`lan3`/`lan4` with dropbear up.
It only becomes bootable after step 3, though — hence the ordering above.

A whole-chip dump needs no special support, since the partitions tile exactly:

```sh
ssh root@192.168.1.1 'for i in 0 1 2 3; do dd if=/dev/mtd$i bs=128k conv=noerror,sync; done' \
  | zstd -T0 -o w1700k-full-512m.img.zst
```

`conv=noerror,sync` so an uncorrectable ECC block pads instead of truncating the
stream. Decompressed size must be exactly 536870912. `zstd` is not in our image,
hence compressing on the far end here.

**Do compress on the device when dumping from stock**, though — measured on unit
`5867a0`, `nanddump -o` reads at ~3.7 MB/s and that is the bottleneck: 16 MiB took
4.85 s wall of which only 0.81 s was user time, so gzip rides along for free.
Erased regions compress ~677:1 (16 MiB of `system` -> 24,775 bytes), so on-device
gzip turns a 446 MiB transfer into tens of megabytes. Whole-flash read is ~2–3
minutes, not the tens of minutes CPU-cost intuition suggests.

`CONFIG_MTD_PARTITIONED_MASTER` would give a whole-chip `/dev/mtd` node, but do
not enable it: the master registers *before* its partitions, so every partition
number shifts by one. `install.sh` hardcodes `/dev/mtd2` for `ubiformat`, which
would then be `chainloader` — and its factory validation would still pass,
because whole-chip offset `0x400000` is the same physical location.

## Where the support came from

Backported from upstream master, which carried this device on kernel 6.12 from
2026-03-11 (`99307582de`) until airoha moved to 6.18 on 2026-06-03
(`bc864d2978`). The 25.12 branch never got it — the merge landed after the branch
point.

Source revision is **`3cc55ea28c^`**, not master, so the DTS matches this tree.

`3cc55ea28c`'s `managed = "in-band-status"` **is applied** on `gdm2` and `gdm4`,
and is required — see *10G ports*. Its `&pon_pcs` half is not: this tree predates
the standalone-PCS migration and has no such node.

Still excluded: **`91fa75d7f4`** removes a dummy PHY LED pinctrl to fix GPS
(gpio33/34 alternate function conflicts with the HSUART the GPS is on). It landed
after 6.12 was dropped and has never run on this kernel. Try it if GPS is silent
on `/dev/ttyS2` @ 460800.

`seeds/kernel-airoha-an7581.seed` disables `SND_SOC_AN7581`. Not cosmetic:
`SND_SOC_AN7581_WM8960` depends on `I2C`, which only becomes set once
`kmod-i2c-an7581` is built — after `build_me.pl` has run `kernel_oldconfig`. The
symbol is then new and unanswerable at compile time, which fails the build. No
an7581 board here has a codec and the `afe` node is already disabled.

## 10G ports

**HW v2 carries an RTL8261CE, not the RTL8261N the wiki and upstream assume.**
The PHYs at mdio 5 and 8 report `0x001cc899` — model `0x09`, revision `9`. Stock
agrees: it loads `rtk-rtl8261ce-phy.ko` and matches `0x1CC890` with the revision
nibble masked. Check this on any new unit instead of assuming; a v1 board with an
RTL8261N would need the other driver.

Two things are required together. Either alone leaves the port negotiating a
link that carries no traffic:

1. **`kmod-phy-rtl8261ce`** — a standalone driver, not the 8261N one. The CE
   keeps its polarity controls behind a vendor OCP window (`MMD1` registers
   `0x7587`-`0x758a`, reaching OCP registers `0x0000` and `0x00c2`), *not* the
   8261N's `MMD30 0xC1` HSI/HSO bits. Writes to `0xC1` are silently discarded on
   this silicon, from the driver and from userspace alike, so the 8261N driver
   cannot configure this part no matter how it is coaxed into binding.
2. **`managed = "in-band-status"`** on `gdm2`/`gdm4`, giving
   `configuring for inband/usxgmii link mode`. USXGMII carries link state in an
   in-band control word; without this phylink runs the MAC in `phy` mode and the
   data path never comes up.

Two 6.12 adaptations live in our copy of the driver, both API drift, neither
touching the recovered register sequences: board polarity is read from the
`realtek,pnswap-tx`/`-rx` properties the DTS already carries, because
`phy_get_tx_polarity()` and `<linux/phy/phy-common-props.h>` do not exist yet;
and hwmon is registered as `"rtl8261ce"` because 6.12 rejects a NULL name with
`-EINVAL` (`probe ... failed with error -22`) and `dev_name()` is unusable, being
`mt7530-0:05`.

**Do not add a CE entry to `rtl8261n`** — both drivers would match `0x001cc89x`
and race. `rtl8261n` carries only upstream's post-reset `mdelay(30)`.

The driver also exposes two `rtl8261ce` hwmon sensors (PHY die temperature,
~55-65 °C), which double as a liveness check that it is really talking to the
silicon. Ports negotiate 5 Gbps against a 5G host NIC.

`mdio-tools` is in the image for this reason: these PHYs are C45, so `phy_id` in
sysfs reads `0x0` and U-Boot cannot help either — it never releases their reset
GPIOs, so they read as all-zero there. Reading their identity needs a tool on the
running system.

## Thermal and cpufreq

The fan is the real mechanism. `S99airoha_fan` programs the vendor curve
(40/50/60/70/80 °C -> PWM 54/69/95/199) into the NCT7802's own auto mode, so it
runs independent of Linux thermal. The 110 °C critical trip also works — critical
handling needs no cooling device. Idle sits around 45 °C.

**cpufreq does not work, and it costs nothing in performance.** The CPU runs at
**1197 MHz**, the top of the 500-1200 MHz OPP table — firmware set it and Linux
never touches it (`cpu_pd/perf_state` is 0). Fixing cpufreq buys idle power and
frequency-based thermal control, not throughput.

Nothing reports the rate: the `cpu` clock reads 0 in
`/sys/kernel/debug/clk/clk_summary` while every other clock is populated. Measure
it with a dependent-ADD chain, which retires one per cycle on the in-order A53.

The cause is a missing device-tree description, not a driver bug.
`ARM_AIROHA_SOC_CPUFREQ`, `AIROHA_CPU_PM_DOMAIN`, `CPUFREQ_DT` and
`CPUFREQ_DT_PLATDEV` are all `=y`, but `grep -r "operating-points\|cpufreq"` over
`arch/arm64/boot/dts/airoha/` returns **nothing**, and the `cpu@N` nodes carry
only `clock-frequency = <80000000>`. `cpufreq_generic_get()` reads a clock that
returns 0, every policy fails, and registration ends in `-ENODEV`. Fixing it
means backporting the CPU OPP table and cpufreq power-domain wiring to match the
driver revision we carry. `CONFIG_CPU_THERMAL` is a later step that cannot matter
until a cpufreq cooling device exists.

## Offload

There is **no WED here** — that is MediaTek's, and airoha has no `mtk_eth_soc`.
The equivalent is the NPU: `CONFIG_NET_AIROHA_NPU=y` plus
`airoha-en7581-mt7996-npu-firmware`, and the DTS wires `airoha,npu = <&npu>` into
the wifi node. **It is active**: `mt76-npu.0`/`mt76-npu.1` appear in
`/proc/interrupts` and carry real traffic, so the wifi side is already offloaded.

These units are dumb APs, so the datapath is **bridged**, not routed. That makes
OpenWrt's `flow_offloading` inert here, and the device state proves it rather
than merely implying it: `flow_offloading` is unset, `nft list ruleset` contains
no flowtable, `/sys/kernel/debug/ppe/bind` lists **0 bound flows**, and
`nf_conntrack_count` sits at ~25 after a 2.8 GB transfer. A flowtable hooks the
forward path and keys off conntrack; bridged frames cross port-to-port at L2 and
never get there, so enabling it would bind nothing. Accelerating this path needs
bridge-specific work.

Measured, bridged WiFi <-> wired (6 GHz 160 MHz, 5 Gbps on the wired side).
AP TX rate to the client is 2402 Mbit/s (`EHT-MCS 11 NSS 2`); client TX to the AP
negotiates higher, 2594-2882 Mbit/s (`EHT-MCS 12`-`13`):

| direction | streams | throughput | peak core | all CPUs | % of PHY |
|---|---|---|---|---|---|
| wifi -> wired | 1 | 806 Mbps | 94% | 44% | 31% |
| wired -> wifi | 1 | 1022 Mbps | 66% | 42% | 43% |
| wifi -> wired | 4 | 810 Mbps | 83% | 45% | 31% |
| wired -> wifi | 4 | 1194 Mbps | 76% | 50% | 50% |

**Uplink is a single-core bottleneck at maximum clock**; downlink no longer is.
Uplink pins one core near 90% and four streams do not beat one, which rules out a
per-flow limit. Downlink now spreads across all four cores and scales with
streams. Hard IRQ affinity is unchanged and still single-CPU — wifi (`mt7996e`,
`mt7996e-hif`, `mt76-npu.*`) entirely on CPU0, ethernet (`airoha_eth.4`, 5.1M
interrupts) entirely on CPU1 — so the spreading comes from softirq steering, not
from the interrupts moving. `packet_steering=2` is set, but `rps_cpus` is `f`
only on `lan2`; `br-lan`, `lan3` and `phy0.2-ap0` are all `0`.

The obvious lever — the in-kernel `nft_flow_offload` L2 bridge series (openwrt
**PR 22533**, 6.12 variant) — was tried here and **rejected**. It requires
`br_netfilter` with `nf_call_iptables=1`, which on a dumb AP means *adding* the
netfilter hook cost to every bridged packet so the flowtable can then bypass it: the
net effect is structurally backwards. Software offload did engage (206 k packets /
818 MB counted `[OFFLOAD]`), but the hardware PPE never bound a single flow — 10 `UNB`
and 0 `BND`, with no error reported — so it bought the overhead without the
acceleration. Fully reverted; do not re-litigate without a reason to expect PPE
binding to work.

`bridger` (eBPF) is not the alternative either: faulty VLAN patch, collapse to
1 Mbit, broken roaming.

Note the wifi side is already NPU-offloaded, so any gain here is on the
bridge/ethernet path, not on wifi.

Uplink runs at 31% of PHY rate against 43-50% downlink. The asymmetry is
unexplained, and uplink is the direction that saturates a core.

## Wireless

Running **6 GHz, channel 37, 160 MHz, WPA3-SAE, MLO off**, country **GT**.

GT is in our `regulatory.db` already — no `wireless-regdb` fetch or reg-table
patching needed, and it beats JP here:

```
(5925 - 6425 @ 320), (N/A, 23), NO-OUTDOOR, AUTO-BW
(6425 - 6525 @ 80),  (N/A, 23), NO-OUTDOOR, AUTO-BW
(6525 - 6875 @ 320), (N/A, 21), NO-OUTDOOR, AUTO-BW
(6875 - 7125 @ 160), (N/A, 21), NO-OUTDOOR, AUTO-BW
```

The full 5925-7125 MHz is available and 320 MHz is permitted in two blocks.
**Channel 37 is deliberate**: it sits in the 23 dBm block, while anything above
6525 drops to 21 dBm. The radio already runs at the 23 dBm cap, so there is no
power headroom to claim without patching the regdb itself. All 6 GHz entries are
`NO-OUTDOOR` — the standard LPI indoor regime.

160 MHz rather than 320: the only 320 MHz- and MLO-capable client here is a
desktop Intel BE200 (2x2); the other machine is an M4 MacBook Pro on Wi-Fi 6E,
which caps at 160 MHz with no MLO. The device wiki also suggests 160 MHz on
6 GHz. Realistic client ceilings are ~1.6-2.1 Gbps (BE200) and ~1.2-1.6 Gbps
(Mac).

**A 6 GHz-only AP is undiscoverable to normal clients.** With no co-located 2.4/5 GHz
BSS in the same ESS there is no RNR to advertise it, and 6 GHz clients do not scan the
band blind: an Android S25+ never showed the SSID at all, and a 6E MacBook listed it
but failed to join without ever sending an auth frame. Keep at least one lower band up
on the same ESS. 6 GHz also mandates WPA3-SAE with `sae_pwe=2` (H2E) and
`ieee80211w=2` (PMF required) — `psk2` and `sae-mixed` are both invalid there, so a
6 GHz radio needs its own SSID entry rather than the shared one.

`mt76` tracks master (`59676919`, 2026-07-01), ahead of 25.12's pin. The MT7996
firmware travels with it — mt76 bundles the blobs — so driver and firmware must
only ever move in one commit. Two `mac80211` patches from master are required for
it to build at all against our backports `6.18.26`: `subsys/321`
(`ieee80211_txq_aql_pending`, for HW-managed-TIM power-save buffering) and
`subsys/390` (`sta_set_airtime_weight`, for HW ATF). Backports itself stays at
`6.18.26`; mt76 needs nothing else master carries.

Note the device's `dnsmasq` refuses to start its DHCP server if another one is
visible on `br-lan` (`found already running DHCP-server on interface 'br-lan'`).
A bench host sharing its connection over a bridged port triggers this, and the
symptom is clients associating and then dropping ~45 s later on DHCP timeout.

  `165-0x` (the multi-netdev/`gdm_dev` series) unlocks HW GRO (`916-02`), the six
  v7.2 fixes still skipped, and plausibly PPE `[HW_OFFLOAD]` binding. It collides
  with our `310-08/09/10` + `604-02` + `606` PCS/phylink work, which has to be
  rebased on top, so it **risks the 10G ports** — do it on the bench unit. Its own
  session; nothing else in flight.
- **Regulatory** — 320 MHz on 6 GHz (GT permits it in two blocks; see *Wireless*) and
  a 30 dBm indoor cap across all bands per SIT, which needs patching `regulatory.db`
  itself since GT tops out at 23 dBm today. Verify measured TX power, not the claimed
  value.
- **IRQ pinning** — collect per-CPU `/proc/interrupts` first, then disable
  `irqbalance` and pin manually at boot. On the deployed unit this has to go through
  the `/etc/monitoring/telemetry` cron sampler, since `dropbear` is disabled there by
  design.
- **cpufreq DTS** — backport the CPU OPP table and cpufreq power-domain wiring.
  The driver patches (`039`, `040`) are already in the stack; only the DTS nodes
  are missing. Power and thermal only, not throughput; the CPU already runs at
  max. Do `CONFIG_CPU_THERMAL` after, not before.
- Explain the 31% vs 43-50% uplink/downlink efficiency asymmetry, and the
  uplink cost of the current `mt76` (-4.5% both stream counts, consistent).
- **Do not port master's `hostapd`.** Ours is 25.12 stable and already carries
  the 2026-1 advisory fix (`c7149e26a9`), so there is no security gap. Master's

  files, `wifi-scripts` 21, `netifd` 7, `ucode` 6 — and taking hostapd alone
  mismatches it against our `netifd`/`wifi-scripts`.
- **`linux-firmware` and `intel-microcode` are standing bumps** driven by the

- ~~`nand-utils` missing from our image~~ — moot. Stock failsafe ships `nanddump`,
